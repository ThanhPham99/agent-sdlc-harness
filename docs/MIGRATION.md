# Migration and Versioning

Canonical runtime state uses schema `agent-sdlc/state/v1` and run records use `agent-sdlc/run/v1`. Provider-specific session/thread identifiers are optional metadata; the canonical `run_id` belongs to the harness.

Use:

```bash
./bin/agent-sdlc compat-check
./bin/agent-sdlc migrate
```

The alpha migration command only performs conversions that are explicitly lossless. Legacy `.ai-workflow` state is detected but not silently rewritten because earlier workflow semantics and evidence fields may differ. For an incompatible project, export durable artifacts/handoffs, initialize v3, and attach those artifacts to the new run.

Protocol, schema, policy, skill and provider package versions are independently traceable in replay/evidence. Breaking canonical schema changes require a major harness version; additive fields should remain backward-readable whenever feasible.

## Layout v1 -> v2 (the shape of `.agent-sdlc/`)

The *shape* of the state directory is versioned separately from the schemas inside it, and is recorded in `.agent-sdlc/LAYOUT.json`. v2 collects everything a run owns into `runs/<run_id>/`, shards the content store, and separates four lifetimes:

| Lifetime | Where | What to do with it |
|---|---|---|
| CONFIG | `project.json`, `workflows/` | Commit it |
| DURABLE | `runs/`, `store/`, `shared/`, `state.json` | Back it up; never hand-edit |
| CACHE | `cache/` | Delete freely; gitignore it |
| DOCS | `docs/` | Regenerated by `report` |

```bash
./bin/agent-sdlc compat-check   # LAYOUT_MIGRATION_REQUIRED on a v1 tree
./bin/agent-sdlc migrate        # converts it
```

What the migration guarantees, and why each matters:

- **It backs up first**, to `.agent-sdlc/.backup-v1-<timestamp>/`, holding the entire pre-migration tree. A re-run reuses that backup rather than taking a second one, so a recovery attempt cannot replace the pristine copy with a half-migrated one.
- **It moves, it does not copy.** A copy would leave the v1 directories in place, and detection keys on their existence — the project would report `compatible: false` forever.
- **It rewrites no content.** On one filesystem every operation is a rename, so an interruption leaves each file at one path or the other, never truncated. If `.agent-sdlc/` spans filesystems the move falls back to copy-then-delete (`EXDEV`); an interruption there can leave a partial copy at the destination, which a re-run reports as `DESTINATION_EXISTS` rather than retrying — delete the partial file and re-run. The source is intact in the backup either way.
- **It never overwrites an existing v2 path.** Replacing v2 data with v1 data is the one outcome worse than stopping.
- **It reports `INCOMPLETE` rather than success** if anything is left behind: a populated legacy directory, a filename v2 cannot address (rename it and re-run), or a move that failed. `LAYOUT.json` records the unfinished work so a later run resumes it.
- **It leaves a healthy v2 project alone**, including one holding files it does not recognise. Only a v1 tree, or one with recorded unfinished work, is touched.

A tree that has been migrated reports `CURRENT` with no markers; that assertion is what the suite checks (`npm run test:layout-migration`).

### Committing `project.json`

`project.json` is CONFIG and worth tracking, but the default `.gitignore` entry is `.agent-sdlc/` — a whole-directory ignore, which git applies before any nested path, so adding the file alone does nothing. Exempt the parent explicitly:

```gitignore
.agent-sdlc/*
!.agent-sdlc/project.json
!.agent-sdlc/workflows/
```

or bypass the rule once with `git add -f .agent-sdlc/project.json`. Ignoring the whole tree remains a reasonable default — most of what is in there is DURABLE or CACHE — so this is a choice, not a correction.

### After migrating: the backup

`.agent-sdlc/.backup-v1-<timestamp>/` is a complete copy of the pre-migration tree, and is usually the largest thing under `.agent-sdlc/`. It has no layout row, so `gc` will never reclaim it. Once `compat-check` reports `compatible: true` and your run history reads correctly, `rm -rf .agent-sdlc/.backup-v1-*` is safe. Until then it is the only route back to v1.

Legacy `.ai-workflow` state is unaffected by this and is still refused rather than converted.

## alpha4 -> alpha5 (task runtime)

Run state (`agent-sdlc/run/v1`) is unchanged; task schemas begin at v1 and are additive.

Existing runs keep working. To give a run the alpha5 task runtime:

```bash
./bin/agent-sdlc task migrate --run-id <id> --dry-run
./bin/agent-sdlc task migrate --run-id <id>
```

The migration reads the run's recorded `task-plan` artifact and materializes a task graph
plus one `CREATED` task record per planned task. It:

- preserves the original plan artifact ref and SHA-256;
- generates stable task IDs only where absent, never rewriting an existing one;
- never marks a generated task DONE;
- marks a run already past `IMPLEMENT` as `LEGACY_STAGE_EVIDENCE` instead of fabricating
  per-task evidence for work that ran stage-level;
- backs up `.agent-sdlc/runs/<run_id>/tasks/` before mutation;
- fails closed on an unknown newer plan schema;
- reports `SKIPPED` when a graph and task records already exist.

A run with no recorded plan artifact reports `NO_PLAN_ARTIFACT` and is left untouched.

Note that `IMPLEMENT.gate_requirements` changed to `implementation_artifact` +
`task_graph_complete`, both derived by `task implementation-complete`. A run already past
`IMPLEMENT` is unaffected; a run sitting *in* `IMPLEMENT` needs either a migrated task
graph or an audited `--force`.

## alpha5 -> alpha6 (intelligence, traceability, delivery)

Purely additive. No run, task or plan schema changed, and no existing gate requirement moved.

New state directories, all created on demand:

```
.agent-sdlc/index/                  repository index (safe to delete; rebuilt on demand)
.agent-sdlc/traceability/           traceability graphs and the invalidation log
.agent-sdlc/delivery/               delivery records
.agent-sdlc/ci-evidence/            revision-bound CI records
evals/regressions/candidates/       regression candidates (never auto-adopted)
```

Nothing needs migrating. To adopt the new capabilities on an existing run:

```bash
./bin/agent-sdlc repo index                 # build the index once
./bin/agent-sdlc trace build --run-id <id>   # build the graph from durable state
./bin/agent-sdlc trace coverage --run-id <id>
```

`.agent-sdlc/index/` is a cache. Deleting it costs one rebuild and nothing else. If
`repo status` reports `stale`, rebuild before relying on an answer.

Two additions change behaviour you may notice:

- Task contexts now include a `REPOSITORY FACTS` block for the task's declared scope. It is
  bounded and anchored to that scope; when the index is unavailable the manifest records
  `unavailable` with a reason instead of failing.
- `runtime/parallel.mjs` uses prefix-aware scope overlap (shared with the task scheduler).
  A task list declaring `src/auth/` and `src/auth/reset.js` is now correctly reported as
  conflicting. File-level lists behave as before.

## 3.0.0-rc3 — `/sdlc-route` becomes `/sdlc-router`

`commands/` is removed. Skills are the only public surface, identical on every
host, and a skill is slash-invocable — so `/sdlc-status`, `/sdlc-task`,
`/sdlc-resume`, `/sdlc-approve` and `/sdlc-doctor` keep working unchanged.

The one rename: `/sdlc-route` is gone. Use `/sdlc-router`. No alias is
provided, because an alias would reintroduce the duplication this change
removes.
